Bit us during the build

8 findings · all worked around

These are the ones that produced a visible bug or forced application-level code to compensate. Each carries the workaround that shipped, and the change that would remove the need for it.

A1 Critical The last thing the user says before hanging up is discarded

observed index.js:558–568 merge · :1520 stop

The voice→chat merge tracks how much of voice.transcript it has already written into messages with a private voicePrevLenRef. When the voice state is not active it does not merge — it fast-forwards that pointer past everything it has not seen. And stop() sets the state to "idle" synchronously, before the final line of the closing utterance has been delivered. The last utterance therefore lands entirely inside the non-active window and is skipped permanently.

The agent's own reply usually survives, because it merged mid-call while the state was still active — which is why the failure presents as “only the user's line is missing,” and why it reads as a rendering bug rather than as data loss.

Workaround shipped

A derived voiceUserEcho memo mirrors voice.transcript and voice.partial and subtracts what the chat already shows. The subtraction is exact — the merge writes precisely line.text.trim() — so it can neither double a message nor fight the SDK's state.

Proper fix: when inactive, merge the unseen lines before advancing the pointer. Or have stop() flush pending transcript lines before setting idle.

A2 High The user's in-progress utterance is never rendered at all

read index.js:592

The merge renders voice.partial only when partial.speaker === "agent". A user partial is dropped by construction, and handleTranscript never commits a non-final line to transcript — so while the user is speaking there is no source anywhere in the SDK that shows what they said. The only chance a user turn has of appearing is its final line, which A1 usually eats.

Workaround shipped

Same memo — it reads voice.partial for the "user" speaker too.

A3 High chat.files has no writer for an agent that emits no snapshot

observed index.js:492 thread load · :831 live snapshot

files is written from exactly two places: a thread's stored state.files on load, and a live STATE_SNAPSHOT event. An agent that writes files through tool calls but never emits a snapshot leaves files as {} for the life of the app. Every surface that resolves a path through it — the present_file card, any preview — renders its empty state, even for a file written seconds earlier.

Workaround shipped

lib/persona/workspace-replay.ts rebuilds the workspace by replaying the transcript instead: write_file args carry the whole body, edit_file carries the spans, read_file returns the content. The snapshot is preferred where both know a file.

A4 High parsePresentedFile returns metadata and no content

observed index.js:319–332 · :817–822

It returns { path, title, description } and nothing else, so even with A3 fixed chat.presentedFile cannot render a preview on its own — the bytes have to come from somewhere the hook does not provide. It also requires status === "success", so a present_file result in any other envelope is treated as “no file was presented”.

Separately, presentedFile is assigned as a side effect of the tool call returning, so binding a sheet to it flings a preview open under the user the moment the agent finishes.

Workaround shipped

The sheet is bound to caller-owned state instead, set by the Open button on the tool card — opening a file is the user's click, not a consequence of the agent running.

A5 High sendMessage silently discards the message while a stream is in flight

read index.js:615

if (!prompt || isStreaming) return; — no error, no queue, no callback, no return value. The caller cannot tell the message was dropped, and because the early return happens before setInput(""), the text stays in the composer too: the send is invisible from both sides. resumeInterrupt routes through the same call, so an interrupt answered while a stream is still running is a silent no-op as well.

Workaround shipped

The composer never offers Send while streaming (it offers Stop instead), and handleSend refuses to send during a history load. The SDK's own guard is the last line of defence rather than the only one.

A6 Medium isMuted survives start()

read index.js:1708–1723 · :1775–1780

start() resets error, endReason, transcript, partial, toolCalls, acceptedTurnSeqRef and state — but not isMuted, which is written only by mute(). startCapture opens a fresh getUserMedia track whose enabled defaults to true, so after a muted call the next call records normally while the UI — reading isMuted — reports the microphone as off. The user's assumption is the dangerous one.

Workaround shipped

handleStartVoice calls voice.mute(false) before voice.start(). Safe because mute() only reaches for a stream if one exists.

A7 Medium Typing during a call sends to the socket and nowhere else

read index.js:1781–1784

sendText writes { type: "voice.text" } to the websocket and returns. It does not clear chat.input, does not append anything to chat.messages, and reports nothing about whether it sent — it silently no-ops when the socket is not OPEN. So the typed text stays in the composer looking unsent, and a call's transcript has no record of the typed turns at all.

Workaround shipped

handleSendToVoice clears the input — but only in listening, thinking and speaking. connecting is excluded on purpose: the SDK creates the socket before it opens and only leaves that state on the server's voice_session_ready, so clearing then would delete text that sendText had just dropped on the floor.

A8 Medium loadThreadMessages ends with an absolute setMessages

observed index.js:490 · :522–542

Not a functional update, so a fetch that started before another action resolves after it and replaces whatever is on screen. Two loads in flight for different threads have no ordering guarantee — the stale one wins if it resolves last. The hook's own auto-load effect fires for any threadId change with an empty list, so calling loadThreadMessages yourself puts a second fetch in flight and creates exactly that race.

Workaround shipped

One loader, not two: switchToThread clears the messages and sets the id in the same tick (so React batches them into one render) and lets the SDK's effect perform the single fetch.

Found by reading, still live

10 findings · none worked around

Traced to lines but not exercised. The app does not currently reach most of these paths — which is the only reason they have not already appeared as bugs.

B1 Critical reload() duplicates the user's message and keeps the stale reply

read index.js:1038–1064 with :662–663

reload finds lastUserIndex and calls setMessages(messages.slice(0, lastUserIndex)), then calls sendMessage(lastUserMessage.content). sendMessage reads the same render's messages closure and builds nextMessages = [...messages, userMessage] from the full pre-slice list, then calls setMessages([...nextMessages, placeholder]).

Both are direct — not functional — updates, so the second supersedes the first. The list ends up as the entire old conversation, plus a duplicate of the user's last message, plus a new placeholder. The previous assistant reply is never removed, which is the one thing reload exists to do.

Not worked around

This app does not call reload. Fix: have reload pass the truncated list explicitly, or build nextMessages from a functional update, or await a state flush before calling sendMessage.

B2 High A STATE_SNAPSHOT that omits a field wipes it

read index.js:826–832 · :364–375

setFiles(normalizeWorkspaceFiles(event.snapshot.files)) — and normalizeWorkspaceFiles does Object.entries(raw || {}), so an absent files becomes {} and clears the workspace. setTodos(event.snapshot.todos) passes the value straight through, so an absent todos sets state to undefined — while the hook's declared return type is todos: PersonaTodo[] (index.d.ts:447, non-optional).

The author knew: the debug line immediately above guards for both cases with ?? {} and ?.length ?? 0. Only the assignments are unguarded. A consumer doing todos.map(...) or todos.length throws; this app happens to survive on one todos?.length inside TodoChecklist.

Suggested fix

Assign only when the field is present: setFiles(normalizeWorkspaceFiles(event.snapshot.files ?? {})) and setTodos(event.snapshot.todos ?? []).

B3 High Chat and voice disagree on how a tool error is spelled

read index.js:288–296 vs :1682–1693

The chat path's isErrorToolContent accepts an error only when the content parses as JSON with status === "error" — and only when the raw string starts with {. The voice path's TOOL_CALL_RESULT handler reads parsed?.error. So a tool that reports failure as {"error": "…"} renders as a successful card in chat and as a failure in voice, while a plain-text error is a success in both.

Two conventions in one package means that whichever one the agent actually emits, one of the two surfaces is lying about the result.

Suggested fix

One predicate shared by both paths, accepting status === "error" or a truthy error, and treating non-JSON content as opaque rather than as success.

B4 High A failed history load is never retried, and clear() does not reset it

read index.js:538 · :463–521 · :452–462

loadedThreadIdRef.current = threadId is assigned before the fetch. If the fetch rejects, loadThreadMessages sets error and returns [] — but the ref still claims the thread is loaded, so the auto-load effect skips it forever. The user sees “How can I help?” on a thread that does have messages, with a small error line as the only clue. And clear() resets messages, error, interrupt, files, todos and presentedFile but not this ref, so clearing and reselecting the same thread shows nothing at all.

Suggested fix

Set the ref after a successful load (or clear it on error), and reset it in clear().

B5 High Tool calls made during a voice call never reach the transcript

read index.js:1557–1568 · :1676–1694 · :544–611

The voice path collects tool calls into voice.toolCalls through its own TOOL_CALL_CHUNK and TOOL_CALL_RESULT handlers, and the hook returns them — but the merge that writes voice turns into chat.messages handles only transcript lines. A call where the agent writes a file or runs a command leaves no trace in the conversation: the transcript after hanging up is user/assistant prose with the work missing.

The two surfaces also name the same thing differently — id on PersonaVoiceToolCall, toolCallId on chat tool calls — so merging them is a translation rather than a concatenation.

B6 Medium The merge's dedupe can swallow a legitimate repeat

read index.js:579–582

Before appending, the merge scans the whole history for any non-voice- message with the same role and the same trimmed content, and skips the line if it finds one. It exists to stop a line being merged twice — but a voice line and a typed line are different events. A user who typed “yes” earlier and then says “yes” during a call loses the voice turn.

The hook already has an exact guard against double-merging on the line above (prev.some(m => m.id === voiceId)). This second, broader one is the bug.

B7 Medium partial is a single slot shared by both speakers

read index.js:1569–1575

setPartial({ id: "partial", speaker, text }) — one object, so a user partial and an agent partial overwrite each other rather than coexisting, and the id is a constant, so consumers cannot key on it. The clear is conditional too: setPartial(prev => prev?.speaker === speaker ? null : prev) only clears when the final line's speaker matches, so a stale partial can outlive the line it belonged to.

B8 Medium History sent to the server is text-only and role-flattened

read index.js:678–681

payloadMessages is built as { role: m.role === "assistant" ? "assistant" : "user", content: m.content }. Filtering reasoning out is deliberate, but every other role — tool, system, anything added later — is sent to the server as a user turn, and tool calls are dropped entirely. On a thread with an id the server presumably holds the real record; on the first send of a new thread there is no id yet, so the model receives the flattened, tool-less history.

B9 Medium A changing stop identity hangs up the live call

read index.js:1522

useEffect4(() => stop, [stop]) uses stop as the effect's own cleanup, so any change in its identity runs it — and stop() closes the websocket and tears down the audio graph. stop depends on voiceLogger, which is logger.child("voice") memoized on logger, and the provider's logger is memoized on getAuthToken among other things.

So this is latent rather than certain: it needs a caller whose getAuthToken is not referentially stable. Where that holds, every provider re-render with a new token function silently drops the user's call. A cleanup guarded on an unmount ref would be immune.

B10 Medium A voice session binds whatever threadId existed at start()

read index.js:1731–1740

The ticket request sends ...threadId ? { threadId } : {}, evaluated when start() runs. The chat side of the same hook stack explicitly supports a lazily-created thread — sendMessage's overrideOptions.threadId accepts a Promise for exactly that — but there is no equivalent here. So the first voice call in a brand-new conversation, made before any thread exists, opens a session with no thread binding, while the chat merge writes its result into the local message list. The two halves of one conversation end up in different places.

Smaller, and internal consistency

6 findings

Not defects in behaviour so much as places where the package disagrees with itself, or where an API's silence costs the caller an hour.

C1 Note Mutations have no error state

read index.js:1245–1296

deleteThread, updateThread, resetThread and bulkDeleteThreads all reject on failure, but the hook's error reflects only fetchThreads. A caller writing the natural void deleteThread(id) gets an unhandled rejection and a sidebar that silently did not change. useFiles' deleteFile and bulkDeleteFiles have the same shape.

C2 Note The XHR fallback has no timeout

read index.js:133–236

xhrStream never assigns xhr.timeout, so the ontimeout handler at :219 is unreachable and the error it constructs can never be raised. On the fallback path (React Native, or any environment without ReadableStream) a stalled response hangs indefinitely instead of failing.

C3 Note Every callback in useChat is rebuilt on every render

read index.js:1011–1021

sendMessage's dependency array includes options — the caller's object literal, which is fresh every render (useChat({ agentId, threadId, voice })). So sendMessage, handleSubmit and reload all change identity on every render, and nothing downstream can memoize on them.

C4 Note Two disjoint stop()s, and no way to stop everything

read index.js:438–451 · :1512–1521

useChat's stop aborts the SSE stream; useVoice's stop closes the call. Neither touches the other. A UI that offers both a Stop and an End call has to know which one it is calling, and there is no single “stop whatever is happening” — the same name on two hooks with different scopes is a trap on first read.

C5 Note An empty result reads as “still running”

read index.js:360

parseSandboxCommand derives status by truthiness: tc.isError ? "error" : tc.result ? "done" : "running". A tool that legitimately returns an empty string is reported as still running, so the card never settles.

C6 Note Provider context identity is tied to getAuthToken

read index.js:34–94 · :1325–1329

The provider's context value is memoized on getAuthToken, and every hook's auto-fetch effect depends on the fetchWithAuth that value provides. So a getAuthToken whose identity changes re-runs the useThreads / useFiles / useAgents fetch effects — in the worst case a fetch loop. Reading the token function through a ref would decouple them.

Where I would start

4 changes
1
B1 — reload() Leaves the wrong conversation on screen: a duplicate user turn and the assistant reply that was meant to be discarded. Smallest fix here, largest wrongness.
2
A1 + A2 — the voice merge pointer Silent, permanent data loss on the most human path in the product. Merge the unseen lines before advancing the pointer, and flush on stop().
3
B2 — snapshot field guarding undefined assigned into a state declared non-optional. It is a two-token fix and it removes a class of consumer crash.
4
A5 + B4 — the silent no-ops Dropped sends and never-retried loads are the failures that cost the most debugging time, because nothing anywhere reports them. A callback or a return value is enough.
